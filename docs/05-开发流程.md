# GameRate 个人开发与 Codex 协作流程

## 1. 个人 Git 流程

GameRate 当前是个人开发项目，使用简单清晰的 Git 流程即可。

- 使用 `main` 单分支开发。
- 每完成一个小功能提交一次。
- 每次提交前先执行 `git status`，确认修改范围。
- 提交前查看关键 diff，避免误提交无关文件。
- 提交后执行 `git push` 推送远程仓库。
- 不需要复杂的 `develop`、`feature/*`、`release/*` 分支流程。
- 不需要 Pull Request 流程，但需要自己进行人工检查。

## 2. 提交信息规范

建议使用清晰、简短、能说明变更目标的提交信息。

示例：

```text
chore(project): 初始化项目结构
docs(project): 补充项目文档
chore(user): 新增用户模块基础结构
feat(game): 新增游戏列表接口
fix(score): 修复评分统计问题
```

常用类型：

| 类型 | 说明 |
|---|---|
| `docs` | 文档修改 |
| `chore` | 项目结构、配置、依赖等非业务变更 |
| `feat` | 新功能 |
| `fix` | 问题修复 |
| `refactor` | 重构 |
| `test` | 测试相关 |
| `sql` | 数据库脚本 |

## 3. Codex 使用流程

为了避免一次性生成过多不可控代码，每次和 Codex 协作时遵循以下规则：

- 每次只给 Codex 一个明确任务。
- 先让 Codex 阅读 `docs` 中相关文档。
- 不让 Codex 一次性写完整项目。
- 不让 Codex 同时修改后端、前端、小程序和数据库的大量内容。
- 每次生成后人工检查文件和逻辑。
- 检查无误后再提交 Git。
- 新增或调整功能时，同步更新相关文档。

推荐任务示例：

```text
请根据 docs/03-数据库设计.md 修改 sql/01-init-schema.sql，只生成建表脚本，不写后端代码。
```

```text
请根据 docs/04-接口设计.md 创建用户模块 Controller、Service、DTO 的基础结构，只写接口骨架，不实现完整业务。
```

## 4. 开发步骤

项目开发顺序：

1. 先文档。
2. 再数据库。
3. 再后端。
4. 再前端。
5. 再小程序。
6. 最后部署。

详细顺序：

- 完成项目规划、功能模块、数据库设计、接口设计。
- 根据数据库设计编写 SQL 脚本。
- 初始化 Spring Boot 基础配置。
- 按模块开发后端接口。
- 使用 Postman 或 Apifox 测试接口。
- 开发 Web 前端页面并联调接口。
- 后续开发小程序端。
- 最后进行服务器部署和线上验证。

## 5. 测试流程

### 单接口测试

- 测试正常请求。
- 测试必填参数为空。
- 测试参数格式错误。
- 测试未登录访问。
- 测试权限不足。
- 测试重复提交。
- 测试数据不存在。

### Postman / Apifox 测试

- 为每个接口建立测试请求。
- 保存接口参数示例。
- 保存成功响应和失败响应示例。
- 重要接口保留测试记录。

### 前后端联调

- 确认前端请求路径、方法、参数和后端一致。
- 确认登录态传递正确。
- 确认错误提示能正常展示。
- 确认分页、筛选、排序结果正确。

### 数据库检查

- 检查表数据是否正确写入。
- 检查评分、评论、收藏统计字段是否同步更新。
- 检查唯一索引是否能防止重复评分和重复收藏。
- 检查删除逻辑是否符合预期。

### 页面功能测试

- 测试首页、列表页、详情页。
- 测试登录注册。
- 测试评分、评论、收藏。
- 测试后台新增、修改、删除游戏。
- 测试排行榜和搜索结果。

## 6. 每次任务完成后的检查清单

- 是否只完成了本次明确目标。
- 是否误改了无关文件。
- 是否同步更新了文档。
- 是否需要新增或调整 SQL。
- 是否需要补充测试记录。
- 是否可以进行一次清晰的 Git 提交。
